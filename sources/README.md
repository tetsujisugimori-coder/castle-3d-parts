# 城郭研究史料台帳（第1層）

[全一覧・城郭別一覧・未入手一覧](index.md) / [仕様](schema/source.schema.json) / [初期調査・検証](../docs/source-register-stage1.md)

史料の書誌と確認状況を管理する。遺構の実在、復元仮説の正しさ、CAD部品の採用を自動承認する機能ではない。第2〜4層のデータベースやWeb検索UIは未実装。

## ファイルとID

- `records/SRC-NNNN.json` を1史料・1版・1分冊に対応させる。IDは城名や年代に依存しない連番で、削除・再利用しない。
- 新規採番前に名称、別題、巻、版、出版者、刊行年、識別子、既存関連IDを検索する。別名だけの重複登録を避ける。
- 別作品は同一事件を扱っていても別史料。改訂版・伝本・分冊を別登録した場合は `related_source_ids` で関連先を指す。これは同一内容・史実一致を意味しない。
- 集合書誌のNCIDは複数分冊を表すことがある。`NCID-set` と明記した集合識別子だけは巻・版を含めて検査する。DOI・NDL・JPNO等は巻を変えても同一識別子の重複を拒否する。自動重複検査は候補検出であり、意味的な同一性の判断はレビューで行う。
- 訂正は理由と根拠をPRへ記載する。統合が必要になっても参照IDを勝手に消さず、移行設計を先にレビューする。

## 記録の意味

- 不明の単一値は `null`、未確認の集合は `[]` とし、事情を `research.unknowns` に残す。架空の文章や仮の数値で穴を埋めない。
- `publication_year/date` は刊行年・日付。Webの更新日、確認日、PDFメタデータの生成日は代用しない。年月しか判明しないときは日を補わない。
- `extent` は書誌の数量表記を保持する。`pdf_pages` は取得ファイルのページ数であり、印刷ページ数とは別。
- `bibliography.evidence_urls` が書誌情報の根拠。第三者目録から得た記述を原本の奥付照合と呼ばない。
- `access.checks` は各URLの読取方法と結果。取得失敗は資料不存在ではない。`pdf_url` は所在確認を示し、ダウンロード成功を意味しない。
- `acquired_sha256` は実際に取得した完全ファイルのSHA-256。原ファイルは台帳に同梱しない。CIはURL到達性・ファイルの取得を自動実行せず、記録形式と参照整合のみを検査する。

### 独立した確認状態

| 軸 | 値と意味 |
| --- | --- |
| bibliography | verified:主要書誌を原本又は目録で確認 / partial:間接確認や未解決あり / unverified:未確認 |
| acquisition | full_file_acquired:ファイル全体取得 / webpage_read:Web本文を実読 / catalog_only:書誌のみ / unavailable:対象版未入手 |
| text | not_checked:研究対象本文は未確認 / partial_checked:記載した箇所のみ確認 |
| figures | not_checked:未照合 / partial_checked:指定図のみ / not_applicable:図版なしと確認した場合のみ |

第1期では全体照合状態（fully_collated）は使用不可。対象版・全体の範囲・方法を検証できる照合記録仕様を追加レビューするまで、部分照合から自動昇格させない。

書誌の表紙・奥付だけを読んでも研究本文の確認には加算しない。ファイル全体の取得と全文照合も別。目録のページを読んだことを本文確認へ昇格させない。

`research.locations` は後から引用できる箇所の台帳であり、遺構データベースではない。`id` は史料内で安定させる。`kind` は引用・要約・作業者の解釈を区別する。本文・図版を実読した範囲を各フラグとlocatorで明示する。原文の疑問符・推定表現を確定に書き換えない。未読箇所に生成した引用・要約を置かない。

## 登録・更新手順

1. 既存ID・版・関連資料とIssue/PRを照合する。
2. 公式Web、PDF、図書館目録を実際に開く。検索抜粋だけの情報は本文確認に使わない。
3. レコードを作成。出典URL、印刷頁・PDF頁（1始まり）・図番号、確認範囲、未確認を記す。
4. `node scripts/source-register.mjs --write` で一覧を再生成する。
5. `node scripts/source-register.mjs` と `node --test` と `node scripts/build-site.mjs` を実行する。
6. 著作権、書誌の同定、確認状態、生成一覧を別担当がレビューし、Draft PRへ提出する。

例: `node scripts/source-register.mjs --site=山中城` は該当JSONを出力する。フィルターは完全一致。資料種別や確認状態は一覧列・JSONから検索できる。

## 検証方式

JSON Schema 2020-12として公開し、リポジトリのNode検査器は本スキーマで使用するキーワードだけを処理する（汎用Schema実装ではない）。未対応キーワードはエラーにし、Schema追加時に黙って検査を抜かない。追加プロパティ、型、必須項目、列挙値、URL、日付、ID・書誌重複、関連ID、確認状態の矛盾、一覧の古さを拒否する。

これは史料内容の真偽を自動判定する機能ではない。将来の全文照合の宣言、目録間の差、別名の意味的重複は人間/独立レビューが必須。公開PDFにリンクしていても再配布許諾とは解釈しない。

## 将来の参照契約

将来は `{source_id: "SRC-0008", location_id: "L02"}` のように史料と箇所を参照する。第2層の観察事実は複数の参照を持ち、1史料から複数の観察事実を作れる。第3層は相反する仮説を別レコードで保持し、第4層のCAD変数・モデル版・採用場所は選んだ仮説を固定参照する。

観察事実・解釈・部品を史料レコードへ押し込まない。`related_source_ids` の関係種別、箇所の版間対応、引用の権利管理は次期設計で追加を検討する。既存 `catalog/wooden-palisade-v0.json` は変更しない。初期史料を登録しただけで木柵v0の存在・寸法を実証済みにしない。
