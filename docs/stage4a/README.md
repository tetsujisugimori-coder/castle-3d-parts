## 保存形式 v2

- `catalog_commit` は上流資産の基準コミット。保存票の `catalog_sha256` はカタログのルートから全フィールドを含む正規化JSONのUTF-8バイトに対するSHA-256（小文字16進64桁）。接続点・方向、部品の版と姿勢、単位・座標系、GLB・manifest参照、GLBハッシュとノード、適用範囲を含む。SHAは外部参照ファイルの実バイトを直接検証しない。固定資産のGLB照合は既存の実バイト試験を用いる。
- 正規化では、各オブジェクトのキーをUTF-16コード単位の辞書順で並べる。配列の順序は保存する。余白、BOM、末尾改行は付けない。値の文字列・数値の表記はECMAScriptの `JSON.stringify` と同じで、有限のIEEE 754倍精度数値のみ、負のゼロは0、UnicodeのNFC/NFD変換は行わない。JSONデータの要素は列挙可能な自前の値プロパティに限り、疎な配列、追加の配列プロパティ、アクセサ、循環、64階層を超えるコンテナを拒否する。読込時は各オブジェクトでエスケープの解釈後に同じ名前となるキーの重複を拒否する。
- `saveAssembly` は新規のv2設計にSHAを付加する。すでにSHAを持つ設計は、実際のカタログから再計算した値と照合する。保存に成功した設計は、同一の固定カタログで再読込でき、配置・回転・接続と正規化した値が一致する。保存・読込ともに文字列最大100万UTF-16コード単位。不正入力時も呼出元のデータを変更しない。
- `loadAssembly` と `validateAssembly` はSHA付きv2を要求し、SHA欠落・不一致、旧v1、未知版を拒否する。v1には保存時のカタログを特定する根拠がないため、自動移行は提供しない。信頼できる版管理済みカタログを呼出元が供給する。SHAで検査するのは内容同一性で、カタログの真正性や史実妥当性には別の根拠が必要となる。
- `catalogSha256`、`validateAssembly`、`saveAssembly`、`loadAssembly` の結果はPromiseで返る。Node.js 22およびセキュアコンテキストのブラウザでWeb Cryptoと `TextEncoder` を使う。座標変換・配置操作は同期APIのまま。
